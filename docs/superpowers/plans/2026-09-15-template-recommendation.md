# 第五阶段：AI 模板推荐

日期：2026-09-15。状态：待实施。先完整阅读 [设计基线](../specs/2026-09-13-kanvi-design.md)、[第四阶段报告](../../validation/2026-09-15-markdown-rendering.md)。主代理实施，子代理仅探索和核验。

## 目标与边界

在已有 Markdown 导入与手选流程中增加“推荐模板”。先由本地程序筛选结构适配且样例规则通过的版本，再让 DeepSeek 排序；返回主推荐、备选和原因，用户仍可手选。AI 不生成、改写或删减原文，不返回任意 HTML、样式代码或未保存模板。

现有接口是 `parseMarkdown`、`templateEligibility`、`TemplateRepository.detail/list`、`completeJson` 与文章生成 API。候选筛选逻辑复用，文章生成时重新检查资格，不信任推荐时的陈旧通过状态。

只做代码、受控模型功能测试、生产构建、HTTP 与必要的官方检查器集成。没有用户配置时不调用真实收费 API；不执行公众号实测或浏览器交互模拟。

## Task 1：候选契约与测试样例

- [ ] 明确输入上限、候选版本 ID、标签及可发送的设计摘要；排除来源正文、密钥、原始参考 HTML、检查器 outerHTML 和整个 Obsidian 仓库。
- [ ] 准备至少三套来自自写参考/受控分析、风格标签不同的纯文字模板，逐一进行实际样例规则检测。保留原风格，不为通过检查删除强调或隐藏上游诊断。
- [ ] 覆盖正文结构不符、样例未通过、检测中、损坏记录、零候选及候选过多等情况；明确展示原因或上限，不自动退到默认模板。

## Task 2：受限推荐与数据发送

- [ ] 默认只发送文章标题、标签、篇幅、结构统计及必要的短片段；在调用前明确显示发送范围。精确片段上限在实现前固定并测试，不能截断后声称包含全文。
- [ ] 使用服务端 `completeJson` 和固定内部提示词；所有文章及模板文字只作为数据，忽略其中改变任务或输出格式的指令。
- [ ] 定义严格响应 schema：主推荐、有限备选、原因；只可引用候选中的精确模板 ID/版本，不接受新增字段、未知 ID、重复推荐、任意样式或正文。
- [ ] 返回理由与实际候选版本绑定；响应无效或 API 超时清楚报错，不自动重试收费请求。

## Task 3：接口、界面与资格重验

- [ ] 生成页增加可选推荐入口，显示发送范围、主推荐、备选和理由；保留手选列表，缺少 Key 仍可正常生成。
- [ ] 输入文档变化后清除旧推荐；取消、超时或返回次序变化不覆盖新文档状态。
- [ ] 推荐返回后及文章生成前重新验证候选版本资格；检测状态变化时提示重新选择，不沿用旧通过结果。
- [ ] 本地按需要保存推荐记录，绑定 Markdown 指纹、候选版本、输入摘要、模型配置及时间，不保存 Key；推荐记录不冒充文章检测报告。

## Task 4：验证与交付

- [ ] 受控响应测试覆盖主推荐/备选、未知或重复版本、无效 JSON、多余字段、提示注入、超时、取消、缺少 Key、无候选与资格变化。
- [ ] 自动验证不会重写原文、无法绕过本篇独立检测，并确认手选不依赖 AI。
- [ ] 完成类型检查、自动测试、生产构建和 HTTP 核验；模型真实建议质量单独注明是否测试。
- [ ] 更新 README、路线、事实报告及第六阶段计划，提交并推送已授权私有 GitHub。开发数据与密钥不进入 Git。

## 完成标准

模型只能在本地判定可用的模板版本中推荐；文章内容与渲染仍由本地保真流程控制。失败不会锁死手选，陈旧推荐不会绕过资格重验或文章独立检测。复杂布局自动重建、编辑器与自动发布不纳入此阶段。
